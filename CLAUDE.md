@AGENTS.md

## Commands

- `npm run dev` — start the Turbopack dev server (defaults to port 3000, falls back to 3001 if occupied)
- `npm run build` — production build (also type-checks via `tsc` as part of the build)
- `npm run start` — run the production build
- `npm run lint` — ESLint (flat config extending `eslint-config-next` core-web-vitals + typescript)
- No test suite is configured in this repo yet.

### Database (Prisma + SQLite)

- `npx prisma migrate dev --name <name>` — create and apply a migration in development
- `npx prisma generate` — regenerate the Prisma Client; **must be run manually after every `schema.prisma` change** (not automatic, and not run automatically by `migrate dev` either). **Restart `npm run dev` afterwards**: `src/lib/prisma.ts` caches the client on `globalThis` in development, so a running dev server keeps serving the pre-`generate` `PrismaClient` instance even after HMR reloads the regenerated files. The symptom is a server-side `Cannot read properties of undefined (reading 'findMany')` on the newly added model, while `npm run build` succeeds — a stale process, not a code bug.
- `npx prisma db seed` — run `prisma/seed.ts`; also not automatic, run explicitly after resetting/seeding data
- `npx prisma studio` — browse/edit local data

## Architecture

**Stack**: Next.js 16 (App Router) + TypeScript, Tailwind CSS v4, Prisma ORM v7 + SQLite, Framer Motion, `lucide-react`. Path alias `@/*` → `./src/*`.

**RTL/Persian by default, English at `/en`**: see *Languages* below. Persian is the default; keep layout direction-safe (logical spacing, `text-start` not `text-right`, no hardcoded left/right assumptions) because the same components now render in LTR too.

**Design system / theme**: the red color scale and `ink-*` text-color scale are defined once in `src/app/globals.css` via Tailwind v4's `@theme inline` (e.g. `--color-red-500`, `--color-ink-900`). These override Tailwind's built-in `red-*` palette with the project's own slightly-dark red, so `bg-red-500` etc. always resolve to the theme, never the default. Use those existing tokens (`bg-red-500`, `text-ink-500`, …) instead of introducing new ad-hoc colors. Base primitives live in `src/components/ui/` (`Button`, `Card`, `Badge`, `Container`, `SectionHeading`, `PlaceholderMedia`); page sections live in `src/components/sections/`.

**Data fetching pattern**: most section components under `src/components/sections/` that show real content (`GalleryPreview`, `BlogPreview`, `TestimonialsPreview`, `PricingPreview`, and the full pages under `src/app/*`) are `async` Server Components that query Prisma directly — there is no API layer for reads. `src/lib/prisma.ts` exports a singleton `prisma` client built from `PrismaClient` + the `PrismaBetterSqlite3` driver adapter (Prisma 7's SQL workflow requires an explicit driver adapter; see `.agents/skills/prisma-database-setup/references/sqlite.md` for the pattern). The generated client lives at `src/generated/prisma` (not `node_modules`) and is imported as `@/generated/prisma/client` — re-run `npx prisma generate` whenever `schema.prisma` changes or these imports go stale.

**SQLite modeling conventions** (see `prisma/schema.prisma`): SQLite has no native enum or scalar-list support, so:
- Enum-like fields (`User.role`, `GalleryItem.type`, `BlogPost`/`Package`/`Order`/`Lead` status-ish fields) are plain `String` columns; the allowed values are documented in a comment above each model rather than enforced by the schema.
- Array data (e.g. `Package.features`) is stored as a JSON-encoded string and `JSON.parse`d at the call site (see `PricingCard`).

**Placeholder-media pattern**: content models have an optional image field (`GalleryItem.url`, `BlogPost.coverImage`, `Testimonial.studentImage`). `src/components/ui/PlaceholderMedia.tsx` renders a real `next/image` when that URL is set, otherwise falls back to a deterministic gradient + icon tile. The fallback icon/gradient variant is derived purely in the presentation layer from `hashVariant(id)` in `src/lib/placeholder-icon.ts` — it is not stored in the database, so don't add icon/variant columns to the schema for this.

**Languages (i18n)**: Persian lives at the unprefixed URL (`/about`), English under `/en` (`/en/about`). Internally every public page is `src/app/[lang]/...`; `src/proxy.ts` *rewrites* unprefixed URLs to `/fa/...` (browser URL unchanged), lets `/en/...` through, and 308-redirects a literal `/fa/...` back to the unprefixed URL. The matcher excludes `_next`, `/uploads`, `/px` and anything with a file extension — a new top-level route outside `[lang]` must be excluded there too. Admin is Persian-only and outside `[lang]`.
- **Strings** live in `src/i18n/dictionaries/fa.ts` (source of the shape) and `en.ts` (typed `Dictionary`, so a missing key fails the build). `getDictionary(lang)` is synchronous so Client Components can use it; Server Components use `getDict()`/`getLocale()` from `src/i18n/server.ts` (built on `next/root-params`, no prop drilling). Client Components and Server Actions get `lang` as a prop / a hidden `locale` form field (`ConsultationForm` → `submitLead`, which also stores `Lead.locale`; the admin leads page shows an EN badge and an English WhatsApp greeting).
- Build internal hrefs with `localePath(lang, "/x")`. Page metadata goes through `pageMetadata()` in `src/i18n/metadata.ts` (canonical + `hreflang`); set `SITE_URL` in production.
- **No IP/geo detection, on purpose** (VPNs, Iranians abroad, static rendering). The navbar switcher is a plain anchor to the same page in the other language; `rememberLocale` writes a `lang` cookie as an enhancement, which `proxy.ts` uses only to send `/` to `/en`. `LanguageSuggestion` (client-only, `useSyncExternalStore`) offers English once on the Persian site when `navigator.languages[0]` is English and no cookie exists.
- **Database content uses optional English columns; blank = fall back to Persian**: `Package.titleEn/periodLabelEn/featuresEn` (`PackageEnglishForm` on `/admin/packages`) and `AboutContent.*En` (`/admin/about`; if the Persian text is still the shipped default, the shipped English default is used — see `getAboutContent(lang)`). Not translated yet: blog posts, gallery captions, testimonials and their form, `/pay/[token]` — these keep a `lang="fa" dir="rtl"` wrapper inside English pages.
- `revalidatePublicSite()` (`src/lib/revalidate.ts`) revalidates `/[lang]` as a whole; use it rather than naming public paths, since `/about` and `/en/about` are one route.
- English forms accept foreign phone numbers: `normalizeContactPhone` returns `09…` for Iranian numbers and `+<digits>` otherwise; `toInternational` handles both.

**Brand name**: `SITE_NAME` in `src/lib/brand.ts` is the single source, along with the logo mark and the tagline; every page's `metadata` title goes through `pageTitle()`. It used to be hard-coded in the navbar, the footer and eight page titles, which made a rename a search-and-replace with no way to tell whether one had been missed. The name is Latin inside an RTL document, so it is rendered inside `<span dir="ltr">`.

**Instagram section**: `InstagramFeed` renders DB-backed cards (`InstagramPost` model) that link out to instagram.com — it deliberately does **not** use Instagram's official `embed.js` blockquote embed or the oEmbed API. Instagram is blocked in Iran and Meta blocks Iranian IPs, so official embeds would render as empty boxes for most of this site's actual audience; oEmbed additionally requires a Meta app token that an Iranian developer account can't obtain. Post metadata also can't be scraped — every post URL hits a login wall unauthenticated — so captions and cover images are entered by hand via `prisma/seed.ts`. Cover images are self-hosted under `public/instagram/<shortcode>.jpg` rather than hotlinked from `scontent.cdninstagram.com`, whose URLs are short-lived, signed, and unreachable from Iran. The account handle, feed size and permalink construction live in `src/lib/instagram.ts` (permalinks are derived from `shortcode` + `type`, not stored); `Button` takes an `external` prop to render a plain new-tab anchor instead of a `next/link`.

- **Posts are added from `/admin/instagram`**: the coach pastes the post's link and uploads a screenshot. `parseInstagramPostUrl` pulls the shortcode out of the link and infers `type` from the `/reel/` vs `/p/` segment, accepting every form Instagram hands out (with or without protocol, `www.`, a `/<username>/` prefix, a trailing slash, or the `?igsh=…` parameter). `/share/…` links are **rejected on purpose** — they carry no shortcode and only resolve by following a redirect, which this server cannot do from Iran; the error tells the coach to copy the address bar URL instead.
- The section is a **rolling window of `INSTAGRAM_FEED_SIZE` (6) posts**, not an archive. Adding one puts it at `sortOrder: 0` and rewrites the whole ordering to 0…n-1 (rather than nudging it, so the column can't drift into gaps or duplicates); anything past the window is deleted along with its uploaded screenshot, which would otherwise be an orphaned file in `public/uploads/`. A seeded post that falls off keeps its repo-shipped `/instagram/*.jpg`, since `deleteUpload` refuses paths outside `/uploads/`.
- Re-adding a post that already exists replaces its screenshot and moves it back to the front instead of failing on the `shortcode` unique constraint.

**Admin panel** (`/admin`): email + password login backed by the existing `User` model (`role === "ADMIN"`). Auth is deliberately dependency-free — `src/lib/auth/password.ts` hashes with Node's built-in `scrypt` (stored as `scrypt$<salt>$<key>`) and `src/lib/auth/session.ts` issues an HMAC-SHA256-signed, httpOnly session cookie. No NextAuth/bcrypt; don't add one without a reason.

- **The authorization boundary is `src/lib/auth/dal.ts`, not the layout.** Next.js layouts don't re-run on client-side navigation and don't stop nested segments from rendering, so *every* admin page and *every* Server Action calls `requireAdmin()` itself. `getAdmin()` re-reads the user's role from the database on each render pass rather than trusting the role claim inside the cookie, so a demoted admin loses access immediately. Server Actions are public HTTP endpoints — a new admin action without its own `requireAdmin()` is an open endpoint.
- `src/proxy.ts` (Next 16 renamed `middleware.ts` → **`proxy.ts`**) only does an optimistic *cookie-presence* check to bounce anonymous visitors early; it intentionally does no signature or database check.
- `ADMIN_SESSION_SECRET` (≥32 chars) is required in production and throws if missing; in development it falls back to a per-process random secret, so restarting `next dev` logs you out.
- The public site and the admin panel are **two root layouts**: `src/app/[lang]/layout.tsx` (document shell + `Navbar`/`Footer`, sets `lang`/`dir`) and `src/app/admin/layout.tsx` (Persian-only shell); `src/app/admin/(panel)/layout.tsx` owns the admin chrome. There is no `src/app/layout.tsx`.
- Uploads go to `public/uploads/` via `src/lib/uploads.ts`, which validates by **magic bytes** (not the client-supplied Content-Type), caps size at 5MB, and names files with a UUID so the original filename is never trusted. `deleteUpload` refuses paths outside `/uploads/`, so repo-shipped images like `/instagram/*` can't be deleted through it. The directory is gitignored except `.gitkeep`. Note `npx prisma db seed` deletes all `GalleryItem` rows, which orphans any files already uploaded into `public/uploads/`.
- The admin account is created by `npx prisma db seed` from `ADMIN_EMAIL`/`ADMIN_PASSWORD`; with no `ADMIN_PASSWORD` it generates a random one and prints it once. Re-seeding never overwrites an existing admin's password.
- Uploads go to `public/uploads/` via `src/lib/uploads.ts`, but they are **served by the route handler at `src/app/uploads/[file]/route.ts`**, not by `public/`. Next.js snapshots the `public/` file list at *build* time, so a photo the coach uploads afterwards 404s for the running server and keeps 404ing after a restart, until the next `next build` — the symptom is an admin panel that accepts the file and stores the row, then shows a broken image everywhere (`next/image` fetches the URL over HTTP and logs "The requested resource isn't a valid image … received null"). The route handler only ever sees requests `public/` couldn't answer, since build-time public files take precedence. It refuses any name that isn't `<uuid>.jpg|png|webp`.
- A `"use server"` file may only export async functions — shared constants like `LEAD_STATUSES` live in `src/lib/leads.ts`, not in `src/lib/actions/leads.ts`.

**Gallery uploads** (`/admin/media`): the whole path is built around one photo not becoming three. Three separate things used to allow that, and all three had to go:

- **The gallery actions end in a redirect, not a returned success.** `finish()` in `src/lib/actions/media.ts` redirects to `/admin/media?ok=<code>&n=<nonce>`, so the browser is left on a GET (Post/Redirect/Get, the same shape `src/lib/actions/blog.ts` already used). Without it the browser sits on the POST that performed the upload, and a refresh re-sends it — a pull-to-refresh on iOS especially, which is exactly the reflex when a page seems stuck. The nonce is load-bearing: two identical outcomes in a row would produce the same URL, and the page (and with it the form, keyed on `n`) would not re-render to clear the picked file. Success messages therefore live in `MEDIA_NOTICES` in `src/lib/media.ts` and travel in the URL; **errors** are still returned as `MediaState` and keep the coach on the form.
- **`GalleryItem.fileHash` is a SHA-256 of the uploaded bytes.** The same bytes under the same caption inside `DUPLICATE_WINDOW_MS` (15 min) are treated as an accidental repeat and no row is created; replacing a photo with the identical photo is a no-op. This is the only duplicate guard that works *before hydration*, which matters because `useActionState`'s `pending` doesn't exist yet then and the form is already natively submittable — no CSS or markup can express "already submitted". The client-side `useRef` guard in both forms is a post-hydration extra, not the mechanism.
- **`prepareUpload` / `writeUpload` in `src/lib/uploads.ts` are split** precisely so the duplicate check happens *before* the bytes hit the disk; writing first would leave an orphan in `public/uploads/` every time a duplicate was refused. `saveUpload` is now a thin wrapper over the two and is unchanged for the blog/about/instagram callers.
- **`serverActions.bodySizeLimit` is raised to 12mb in `next.config.ts`.** The 1MB default is *below one photo from a phone*, and a body over the cap is rejected **before the action runs**, so the action's own error state never reaches the form — the panel simply appears to do nothing, and the coach retries, which is where the extra copies came from. This was reported as "uploads work on desktop and Android but not on iPhone": an iPhone shoots HEIC and Safari re-encodes it to full-resolution JPEG on upload (several MB), while the files that "worked" happened to be smaller. The limit sits above `MAX_UPLOAD_BYTES` (5MB) on purpose, so an oversized file is refused by our own check with a readable Persian message. A reverse proxy in front of the app needs its own limit raised too — nginx's `client_max_body_size` also defaults to 1MB and fails just as silently.
- **`src/lib/image-compress.ts` + `MediaFileInput` downscale the photo in the browser** (longest edge 2000px, JPEG q0.82) by writing back into `input.files`, so the browser's own `FormData` still carries it. It is a **pure enhancement**: no JS, an old browser, or an image the browser can't decode all fall through to submitting the original, which the server validates as before. It also happens to convert HEIC on iOS, where Safari can decode it — elsewhere `decode()` rejects and the server's format error is shown instead.

**Gallery video**: the gallery takes MP4, MOV and WebM alongside images, capped at `MAX_VIDEO_BYTES` (45MB) against the images' `MAX_UPLOAD_BYTES` (5MB).

- **The kind is sniffed, never chosen.** `prepareUpload(file, { allowVideo: true })` returns `kind: "IMAGE" | "VIDEO"` from the magic bytes and that is what lands in `GalleryItem.type`. The upload form used to carry a نوع dropdown, which let a JPEG be filed as "ویدیو" and stored an image wearing a play badge; the dropdown is gone. Video is opt-in per call site, so the blog cover, the about photo and the Instagram screenshot stay image-only.
- MP4, MOV and HEIF share the ISO base-media container, so they are told apart by the brand at bytes 8–12 of the `ftyp` box. HEIF is recognised **only to be refused with a specific message** — an iPhone photo that reached the server untranscoded gets "این عکس با فرمت HEIC آیفون است…" instead of a generic "not an image".
- **`src/app/uploads/[file]/route.ts` answers Range requests** (206 + `Content-Range`, 416 when unsatisfiable) and streams via `createReadStream` instead of `readFile`. This is not an optimisation: iOS Safari will not start a `<video>` whose server answers with a plain 200, so uploaded clips would simply never play on the coach's own phone. Streaming also stops a 40MB clip being read into memory in full on every request. Note the file list `public/` serves is snapshotted at **server start**, not only at build — a file written while the server runs is what reaches this route, which is exactly the upload case.
- `GalleryTile` renders a `<video preload="metadata">` with a `#t=0.1` fragment for the thumbnail; without the fragment a video with no poster paints a black rectangle.
- **`serverActions.bodySizeLimit` is global and two Server Actions are public**, so `src/proxy.ts` now also rejects POSTs over 256KB on `/contact` and `/testimonials`. Raising the limit to 50MB for the admin gallery would otherwise hand anonymous visitors a 50MB write to two actions that still have no rate limiting.

**Gallery lightbox** (`/gallery`): tapping an item opens it full-screen. `GalleryLightbox` is built on **`:target`**, not React state — the tile is a link to `#media-<id>` and the `[data-lightbox]` rules in `globals.css` reveal the matching panel. It therefore works on the first paint, before hydration and with JS off, for the same reason the consultation stepper is CSS-only and the visit counter is an `<img>`; a React lightbox would be a dead tap for however long hydration takes. Prev/next and close are ordinary anchors, so the back button works and each opened item is a real history entry. Panels are rendered from the *full* item list rather than the filtered one, so a link can never point at a panel the current tab removed, and only items that actually have a file get one. Images in the gallery use `fit="contain"` (`PlaceholderMedia` gained a `fit` prop) so a portrait photo is shown whole instead of being cropped to the square tile; `cover` remains the default everywhere else.


**Blog posts** (`/admin/blog`): full create/edit/delete, with a draft state (`published`) so a half-written post stays off the site. `/admin/blog/new` and `/admin/blog/[id]` share one editor, `BlogPostForm` — the two differ only in which action they submit to, which is what stops the create and edit forms drifting apart. `src/lib/blog.ts` holds the limits, `slugify`, `readTime` and `blogParagraphs` with no Prisma import, because the editor is a Client Component (same split as `src/lib/leads.ts` vs `src/lib/actions/leads.ts`); `readTime` used to be copy-pasted into both `BlogCard` and the post page and is now imported from there.

- **Slugs may be Persian.** `slugify` keeps Persian letters rather than stripping them, so a coach who writes an all-Persian title and never touches the optional slug field still gets a working, readable URL instead of an empty string. This only works because `/blog/[slug]` **decodes** `params.slug` before querying: Next.js hands a dynamic param to the page still percent-encoded, so a non-ASCII slug silently 404s without it — and confusingly, `generateMetadata` still resolves the post, so the 404 page comes back carrying the right `<title>`.
- Anywhere a slug is printed next to its `/blog/` prefix it is wrapped in `<bdi>`. A Persian slug is an RTL run inside an LTR path, and without isolation the prefix is reordered to the far end so the URL reads backwards.
- The slug field is pre-filled when editing, so changing a title does **not** change the URL of a post people may already have linked to. Clashes get a numeric suffix rather than an error, and the save message says so when the URL it used differs from the one asked for.
- `publishedAt` is stamped the first time a post goes live and then left alone, so re-editing an old post doesn't shuffle it back to the top of `/blog` (which orders by `publishedAt`).
- Every save revalidates `/blog`, `/`, and both the new and the *old* slug's page, since renaming a post leaves a stale prerender behind at the previous URL.
- `prisma/seed.ts` upserts the six starter posts with `update: {}` — create-only, so re-seeding can't overwrite posts the coach has rewritten. (Packages are the exception: the seed still wipes and recreates those.)

**Public write paths**: two Server Actions are deliberately unauthenticated — `src/lib/actions/submit-testimonial.ts` and `src/lib/actions/submit-lead.ts`. They live in their own files, apart from the admin actions, precisely so the "every action here calls `requireAdmin()`" rule above stays true by inspection. Neither can escalate: the testimonial action can only create rows with `approved: false`, and the lead action can only create rows with `status: "NEW"`. Both re-validate every choice against the allow-lists in `src/lib/consultation.ts` rather than trusting the browser, since HTML constraints (`required`, `minlength`, radio values) are trivially bypassable. Neither has rate limiting yet — that's the known gap if spam appears.

**Consultation form**: `/contact` renders a 6-step form (4 quiz questions → injury question → contact details). All steps stay mounted and are hidden with CSS, so the browser's native `FormData` carries every answer on submit and answers survive stepping backwards — don't "fix" this into per-step React state. Phone handling lives in `src/lib/phone.ts` (Persian/Arabic-Indic digits normalised to ASCII, `+98`/`0098` accepted, stored as `09xxxxxxxxx`). Four details there exist because of real mobile bugs, so don't undo them:

- The step area has a `min-h-80` and every step change calls `scrollIntoView`. Steps have 2–4 options, so without these the form's height changes and the nav buttons slide out from under the user's finger — a phone user taps the same spot twice and it reads as "the next button is broken". Measured: the button drifted 58px per step before, and is now fixed on screen across steps.
- **Stepping is native, not React state.** The current step is a hidden radio group (`name="__step"`, ids `#wz-0`…`#wz-5`) and the nav controls are `<label for>` elements; the `[data-wz-step]` rules in `globals.css` show the panel, counter, progress width and nav pair belonging to the checked step. Elements needing a display other than `block` set `--wz-display` themselves (e.g. `[--wz-display:inline-flex]`). This replaced an `onClick`-driven wizard whose "next" button was a **silent no-op until hydration finished** — measured at ~10s on a throttled mobile connection, during which the page looked completely ready but nothing happened when tapped. That was the actual cause of "the next button doesn't work on mobile"; it was invisible on desktop because hydration lands in ~200ms there. A `<noscript>` block does *not* cover this case, since JS is enabled and merely late — which is why the old one was removed. The radios must stay direct children of the form and precede everything they control (the CSS reaches the rest through `#wz-N:checked ~ *`). React now only adds the "you skipped a question" guard (a `preventDefault()` on the label's click) and the re-anchoring, both pure enhancements — `submitLead` re-validates every answer anyway.
- The injury note is revealed by `.wz-injury:has(#wz-injury-no:checked) … { display: none }` — deliberately phrased as *hide on "no"* rather than *show on "yes"*, so a browser without `:has()` drops the rule and leaves the optional note always visible instead of unreachable.
- **Never combine `hidden` with another display utility** (`inline-flex`, `flex`, …) on the same element — they're both `display`, so which one wins depends on Tailwind's emitted CSS order, not the class list. Use a ternary picking exactly one. This shipped both the "next" and "submit" buttons visible at once until it was caught.

**About section content** (`/admin/about`): the "درباره من" copy and photo are one row in `AboutContent` (fixed id `"about"`), rendered by both `AboutPreview` on the homepage and `/about` — one record on purpose, so the two can't drift apart. `src/lib/about.ts` holds the defaults, length caps and `aboutParagraphs`, with no Prisma import, because the admin form is a Client Component; the database read is `getAboutContent()` in `src/lib/about-content.ts` (same split as `src/lib/leads.ts` vs `src/lib/actions/leads.ts`). A missing row falls back to `ABOUT_DEFAULTS` rather than rendering blank headings, which is also why `prisma/seed.ts` deliberately does **not** create this row — re-seeding then can't wipe the coach's edited text the way it wipes packages. `bodyText` stores the /about paragraphs separated by blank lines (CRLF normalised to LF on save). `/` and `/about` stay statically rendered and are refreshed by `revalidatePath` on save, unlike `/pricing` which is `force-dynamic`.

**Visit counting** (`/admin/analytics`): first-party and self-hosted, because hosted analytics (Google Analytics, Plausible Cloud, …) are either blocked from Iran or block Iranian IPs, so the script would silently fail to load for most of this site's audience. The counter is a 1×1 GIF — `src/app/px/route.ts`, embedded as a plain `<img>` by `ViewPixel` in `src/app/(site)/layout.tsx` — **not** a script: an image is fetched with no JS involved, so a visitor whose JS is blocked or still loading is counted like everyone else (the same principle as the consultation form's CSS-only stepper), and the public pages can stay statically rendered because the pixel URL is constant. The page being counted comes from the `Referer` header, which is also why the `<img>` sets `referrerPolicy="same-origin"`.

- **No IP is ever stored.** `PageView.visitorHash` is an HMAC of IP + User-Agent under a salt re-derived every calendar month. The month-length (not day-length) rotation is deliberate: it is what makes `COUNT(DISTINCT visitorHash)` a correct "how many people" figure for a day *and* for the whole month. The flip side is that people are only ever counted within one salt period — the all-time card shows views only, since a distinct count across months would be person-months, not people.
- `day` and `month` are stored as pre-computed **Jalali** strings (`"1405-06-05"`, `"1405-06"`) in Tehran time, not derived from `createdAt`. SQLite's date functions are UTC-only and know nothing about the Persian calendar, so grouping on the timestamp would put Tehran's evening traffic on the previous day and split a Persian month across two buckets.
- `COUNT(DISTINCT …)` has no Prisma Client equivalent (`groupBy` only counts rows), so the two figures come from `$queryRaw`. Buckets are built from the generated key list, not from the returned rows, so a period with no traffic shows a zero instead of vanishing.
- Bots are filtered by User-Agent, `/admin` is never counted, and `/pay/<token>` is collapsed to `/pay/[token]` so an invoice token never lands in the analytics table. Retention is 400 days, pruned opportunistically on ~1% of pixel requests since the single-VPS deployment has no cron worker.

**The plans themselves**: every package is online (`type: "ONLINE"`) — the audience is students both inside and outside Iran, and in-person coaching in Shiraz is arranged by message rather than sold as a package, so `/pricing` ends with a "پیام بده" note instead of listing in-person plans. There used to be an online/in-person tab switcher (`PricingTabs`); it was deleted rather than left with one empty tab, which also removed a JS dependency — the tabs were React state, so a visitor whose JS hadn't run or hadn't finished hydrating could only ever see the first tab, exactly the failure the consultation form's "next" button had.

Prices change often, so they are **edited from `/admin/packages`, not from the seed** — re-running `npx prisma db seed` wipes and recreates all packages and will discard those edits. `/pricing` is `force-dynamic` so a price change shows up without a rebuild. Only one package may carry the `highlighted` ("پیشنهادی") badge: `setHighlightedPackage` clears it everywhere else in the same transaction, and clicking it on the plan that already has it turns it off. Admin-typed prices go through `parsePriceToman` in `src/lib/orders.ts`, which accepts Persian/Arabic-Indic digits and any separator people type, and rejects absurd values (`MAX_PRICE_TOMAN`) because the usual typo is one extra zero.

**Buying a plan / payment links**: choosing a plan is **not** gated behind the consultation form, and there is no public sign-up anywhere on the site. The pricing cards' CTA is direct contact (WhatsApp/call, plan name pre-filled) and `ContactBand` puts the coach's number on the page in large bold type; the consultation form is offered underneath as the secondary option, for people who want free advice rather than a plan. The coach's own number lives in `src/lib/site-contact.ts` (the counterpart to `contact-links.ts`, which points at a *lead*).

Payment is an invoice the coach issues by hand: `/admin/orders` creates an `Order` with a random 128-bit `token`, and `/pay/[token]` is a public page that anyone holding the link can open — the token *is* the authorization, which is why it's `randomBytes`, not a cuid, and why links expire (`PAYMENT_LINK_TTL_DAYS`). `Order` therefore has **no `userId`**; it carries `customerName`/`customerPhone` directly. The pay page deliberately doesn't select `customerPhone`, and is `noindex` + `force-dynamic`.

- **Money units.** `Package.priceToman` is in *whole toman*; `Order.amountRial` is in *rial* (what gateways settle in). Both column names carry their unit on purpose, so a call site assigning one to the other is wrong on its face. Convert only through the helpers in `src/lib/orders.ts` — never multiply by a literal at a call site. `priceToman` used to be a bare `price` holding *thousands* of toman; it was converted (migration `20260820000100_package_price_toman`) when prices became admin-editable, because a column that silently meant "thousands" turned every price edit into a factor-of-1000 guess.
- No payment gateway is connected yet: Iranian PSPs need e-Namad, which is still in progress, so there is no credential to test an integration against and none was written. `src/lib/payments.ts` is the single seam, and documents exactly what connecting one will require (verify server-side, idempotent callback, re-read the amount from the DB). The `gateway`/`gatewayAuthority`/`gatewayRefId` columns already exist and are named generically, so connecting one needs no migration.

**Replying to leads**: `src/lib/contact-links.ts` builds one-click WhatsApp/Telegram/call/SMS links from the stored phone number. There is no such thing as a separate "WhatsApp ID" — the phone number *is* the WhatsApp identity (`wa.me/<e164>`), and Telegram resolves numbers too (`t.me/+<e164>`, see https://core.telegram.org/api/links). The optional `Lead.telegramUsername` exists only because the Telegram phone link fails when the recipient restricts "Who can find me by my phone number"; when present it's preferred. Don't add per-channel ID fields beyond this.

**Routing**: public marketing pages are plain routes under `src/app/` (`/about`, `/gallery`, `/pricing`, `/blog`, `/blog/[slug]`, `/testimonials`, `/contact`). `/blog/[slug]` uses `generateStaticParams` sourced from Prisma at build time, but `dynamicParams` is left at its default of `true`, so a post published from `/admin/blog` afterwards is rendered on demand and needs **no** rebuild — only the prerendered ones are static. The homepage (`src/app/page.tsx`) deliberately renders only lightweight *preview* sections (a handful of items per section, e.g. `GalleryPreview.take: 6`) that link out to the corresponding full page — this is an intentional perf pattern (keep the homepage fast despite covering every content type), not a gap to "complete" by inlining full lists.

**Animation**: `src/components/motion/FadeIn.tsx` is currently a plain passthrough wrapper with no animation. This was deliberate — an earlier scroll/mount-triggered Framer Motion version left content at `opacity: 0` whenever the animation failed to run on a given device, so content visibility must never depend on client-side JS/animation state. If animation is reintroduced here, it must not gate the first paint of any text/content on JS executing.

**Why SQLite in production**: the DB is intentionally SQLite (a single file, `DATABASE_URL="file:./dev.db"`), not Postgres — chosen after pricing out managed Postgres/object-storage services as unnecessarily expensive for this project's scale. Production deploys to a single low-cost VPS with the app, SQLite file, and an `uploads/` directory for media all on the same box, rather than split managed services. Don't "upgrade" this to a hosted Postgres/object-storage setup without that context.
